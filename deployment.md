## 1. Что такое TyProxy и как он работает

TyProxy — легковесный асинхронный (один runtime `tokio`) сетевой туннель на Rust, который инкапсулирует трафик внутри **TLS 1.3** сессии (rustls + ring), маскируя его под обычное HTTPS-соединение.

### Архитектура (по исходному коду)

* Один бинарник `typroxy` выполняет **обе роли**. Роль выбирается полем `mode` в `config.toml`:
  * `"server"` — запуск сервера (`run_server`);
  * `"client"` — запуск клиента (`run_client`);
  * `"ask"` — интерактивный выбор в терминале (1 — сервер, 2 — клиент; любой другой ввод трактуется как «сервер»).
  * Флаг командной строки `--server` принудительно включает серверный режим независимо от конфига.
* Другие аргументы CLI: `-c/--config <путь>` — путь к конфигу (по умолчанию `config.toml` в текущей директории).
* **Протокол поверх TLS**: каждый кадр имеет 2-байтный big-endian заголовок длины, затем байт типа пакета (`0` — TCP, `1` — UDP, `2` — сырой IP-пакет TUN), 8-байтный идентификатор соединения, 2-байтную длину строки «хост:порт» назначения и полезную нагрузку. Максимальный размер кадра ограничен `u16`, то есть ≈64 КБ.
* **ALPN** обеих сторон жестко задан как `typroxy` — это часть маскировки и одновременно требование: handshake не пройдет, если ALPN не согласуется.
* **Сервер** принимает TLS-соединения, резолвит домены и открывает исходящие TCP/UDP-соединения от своего имени (то есть сервер является открытым relay-узлом для всех подключившихся клиентов — см. раздел «Безопасность»).
* **Клиент** предлагает два взаимозаменяемых модуля перехвата трафика (выбор полем `routing_mode`):
  * `socks5` — локальный SOCKS5-прокси на `socks_bind_addr` (TCP CONNECT + UDP ASSOCIATE);
  * `tun` — виртуальный L3-интерфейс, перехватывающий весь трафик ОС.

### Важные особенности реализации, влияющие на деплой

1. **Одно TLS-соединение на клиент.** Клиент при старте устанавливает ОДНО соединение с сервером; и SOCKS5-, и TUN-сессии мультиплексируются поверх него. Обрыв соединения роняет все активные сессии; **автоматического переподключения нет** — процесс просто печатает «Потеряно соединение с сервером» и завершает цикл чтения (для надежной работы нужен systemd-рестарт, см. раздел 9).
2. **Конфиг генерируется при первом запуске.** Если файла `config.toml` нет, программа создает его с комментариями и **завершается с кодом 0**. То есть первый запуск — всегда «холостой»: нужно отредактировать файл и запустить повторно. Это критично для systemd (`Restart=` может устроить цикл «запустился–вышел», пока конфиг не подготовлен вручную).
3. **Сертификаты не хранятся.** Серверная пара ключ/сертификат генерируется `rcgen` **в памяти при каждом запуске** (CN `typroxy`). На диске сертификатов нет; после рестарта сервиса сертификат меняется — для клиентов это не проблема, т.к. верификация отключена (см. п. 4 ниже).
4. **Верификация сертификата сервера клиентом отсутствует.** В `crypto.rs` используется `NoCertificateVerification` — клиент доверяет любому сертификату. Туннель шифруется, но **не аутентифицируется**: MITM теоретически возможен. Практический вывод для хостера: злоумышленник, перехвативший маршрут, сможет деанонимизировать трафик клиента; для личного использования риск обычно приемлем, но знать об этом обязательно.
5. **Поле `wallet_path` в конфиге ни на что не влияет.** В коде оно читается, но нигде не используется (ни токенов, ни паролей нет). Доступ к серверу имеет **любой**, кто знает адрес `IP:порт` (и ALPN `typroxy`, который зашит в бинарник). Единственная «защита» — неизвестность адреса/порта.
6. **TUN-режим существует только на Linux** — и на сервере, и на клиенте (`cfg(target_os = "linux")`, зависимость `tokio-tun` подключается только для linux-таргета). На macOS/Windows/FreeBSD клиентский режим `tun` вернет ошибку `UnsupportedPlatform`, серверный `tun_enabled=true` выведет предупреждение и продолжит работу без TUN.

## 2. Ограничения платформы (важно перед началом)

| Компонент | Linux | Windows | macOS | FreeBSD |
|---|---|---|---|---|
| Сервер: TLS + SOCKS5-relay (`mode=server`) | ✅ | ✅ | ✅ | ✅ |
| Сервер: TUN + NAT (`tun_enabled`) | ✅ | ❌ | ❌ | ❌ |
| Клиент: режим `socks5` | ✅ | ✅ | ✅ | ✅ |
| Клиент: режим `tun` | ✅ | ❌ (роутинг-код есть, но создание TUN-устройства не реализовано) | ❌ | ❌ |

Практический вывод:

* **Хостить сервер следует на Linux** (x86_64 или ARM) — только там доступна полная функциональность, включая VPN-режим TUN и автоматическую настройку iptables.
* Клиенты под Windows/macOS могут работать **только через SOCKS5** (браузер, Telegram, Proxifier и т.п.).
* Если вам нужен «VPN на весь компьютер» под Windows/macOS — используйте на этих машинах сторонний проксификатор поверх SOCKS5, либо Linux-машину в роли шлюза (роутер, мини-ПК, контейнер).

## 3. Требования к серверу для хостинга

### 3.1. Выбор VPS/выделенного сервера

* **ОС:** любой современный дистрибутив Linux с `systemd` и ядром ≥ 4.x: Debian 11/12, Ubuntu 22.04/24.04, Fedora, Arch. Требуется доступ к `/dev/net/tun` (в стандартных VPS есть; в некоторых контейнерах/LXC — нужно пробрасывать).
* **Архитектура:** x86_64 (amd64) или aarch64 (ARM — например, Oracle Cloud Free Tier). Бинарники Makefile собираются для `x86_64`; для ARM соберите `cargo build --release --target aarch64-unknown-linux-gnu` или прямо на сервере.
* **Ресурсы:** достаточно минимального тарифа (1 vCPU / 512 МБ – 1 ГБ RAM). Нагрузка — проксирование через TLS; узкое место обычно канал.
* **IP-адрес:** крайне желателен **чистый IPv4** от провайдера, который не блокирует нестандартные порты и не режет исходящий трафик. Избегайте провайдеров, чьи IP-диапазоны уже «грязные» (попадают в региональные блокировки) — иначе сам туннель будет недоступен из дома.
* **Трафик:** считайте расход по обоим направлениям (входящий от клиента + исходящий к целевым сайтам удваивает потребление).

### 3.2. Порты и протоколы

* TyProxy использует **только TCP** — и для данных, и для UDP-релеинга (UDP инкапсулируется в TLS-фреймы поверх TCP). Отдельных UDP-портов открывать не нужно.
* По умолчанию сервер слушает `0.0.0.0:8888`. Порт произвольный; рекомендуется заменить на нестандартный или, наоборот, замаскировать под `443`/`8443` (см. раздел 13 — при наличии на сервере реального HTTPS-сервера порты придется согласовать).

### 3.3. Права

* Сервер в режиме TUN требует **root** (создание интерфейса, `sysctl`, `iptables`).
* Сервер в чисто relay/TLS-режиме (без TUN) может работать без root, но тогда клиенты в TUN-режиме не получат выход в интернет.
* Клиент в SOCKS5-режиме работает **без прав**; в TUN-режиме — **только от root/sudo**.

## 4. Полная сборка из исходников

### 4.1. Установка тулчейна Rust

```bash
# rustup (официальный установщик)
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y
source "$HOME/.cargo/env"

# Проверка
cargo --version   # >= 1.70 (edition 2021)
rustc --version
```

### 4.2. Системные зависимости для сборки (Linux)

```bash
# Debian/Ubuntu
sudo apt-get update
sudo apt-get install -y build-essential pkg-config libssl-dev git

# Fedora/RHEL
sudo dnf install -y gcc make pkgconf-pkg-config openssl-devel git
```

(`libssl-dev` формально не нужен — проект использует pure-Rust `rustls`/`ring`, но `build-essential` обязателен для линковки C-кода в `ring`.)

### 4.3. Получение исходников

```bash
git clone https://github.com/lohrrrr/TyProxy.git
cd TyProxy
```

### 4.4. Сборка под текущую платформу

```bash
# Простая релизная сборка (рекомендуется для сервера — собирайте прямо на нем или на совместимой машине)
cargo build --release
# Результат: target/release/typroxy

# Либо через Makefile (собирает x86_64-linux и кладет в ./dist/)
make linux
# Результат: dist/typroxy-linux-amd64
```

Проверка работоспособности бинарника:

```bash
./target/release/typroxy --help
# Должна печатиться справка clap (--config, --server)
```

### 4.5. Что именно собирается

В `Cargo.toml` ключевые зависимости: `clap` (CLI), `tokio` (async runtime, features=full), `rustls` + `tokio-rustls` (TLS 1.3, провайдер ring), `rcgen` (генерация самоподписанных сертификатов в памяти), `serde`+`toml` (конфиг), `thiserror`, и `tokio-tun` — **только для linux-таргета** (отсюда таблица ограничений в разделе 2).

## 5. Кросс-компиляция под другие ОС

Если сервер/клиенты отличаются архитектурой от машины сборки:

```bash
# Добавить таргеты
rustup target add x86_64-unknown-linux-gnu aarch64-unknown-linux-gnu \
                  x86_64-pc-windows-gnu aarch64-apple-darwin \
                  x86_64-apple-darwin x86_64-unknown-freebsd

# Linux x86_64 (нативно или cross-компилятор gcc-x86-64-linux-gnu)
make linux

# Windows .exe (нужен mingw-w64: sudo apt-get install -y mingw-w64)
make windows

# macOS (Apple Silicon / Intel) и FreeBSD — через zig:
# 1) установить zig пакетным менеджером или с ziglang.org/download
# 2) cargo install --locked cargo-zigbuild
make darwin         # aarch64-apple-darwin
make darwin-intel   # x86_64-apple-darwin
make bsd            # x86_64-unknown-freebsd
```

Все артефакты складываются в `./dist/`:

```
dist/typroxy-linux-amd64
dist/typroxy-windows-amd64.exe
dist/typroxy-darwin-arm64
dist/typroxy-darwin-amd64
dist/typroxy-freebsd-amd64
```

Для ARM-Linux добавьте цель вручную: `cargo build --release --target aarch64-unknown-linux-gnu` (понадобится `gcc-aarch64-linux-gnu`).

## 6. Формат конфигурации `config.toml`

Файл ищется **в текущей рабочей директории** под именем `config.toml` (или по пути из `--config`). Если его нет — он создается автоматически, и программа завершается. Полный набор полей (ровно как в `src/config.rs`):

```toml
# Режим запуска: "server", "client" или "ask" (интерактивный выбор)
mode = "ask"

[server]
bind_addr   = "0.0.0.0:8888"    # адрес/порт прослушивания TLS
wallet_path = "server.wallet"   # ВНИМАНИЕ: поле декоративное, кодом не используется
tun_enabled = true              # создавать TUN-интерфейс на сервере (только Linux)
tun_name    = "typroxy-srv"     # имя серверного TUN-интерфейса
tun_ip      = "10.8.0.1"        # IP серверного TUN-интерфейса

[client]
server_host     = "IP_ВАШЕГО_СЕРВЕРА:8888"  # адрес сервера (host:port)
routing_mode    = "tun"          # "socks5" или "tun"
socks_bind_addr = "127.0.0.1:1080"  # локальный SOCKS5 (TCP+UDP)
tun_name        = "typroxy-tun"  # имя клиентского TUN-интерфейса
tun_ip          = "10.8.0.2"     # адрес, который получит клиент внутри туннеля
tun_gateway     = "10.8.0.1"     # «виртуальный» шлюз туннеля (= tun_ip сервера)
```

Замечания по семантике (из кода):

* Сервер **жестко** назначает себе destination-адрес `10.8.0.2` на TUN-интерфейсе и netmask `/24`, а NAT-правила строит для подсети `10.8.0.0/24`. Меняя `tun_ip` сервера, не меняйте адресацию так, чтобы клиентский `tun_ip` перестал быть `10.8.0.2`, а подсеть — `10.8.0.0/24` — маршрутизация сломается.
* Клиентские маршруты добавляются как `0.0.0.0/1` + `128.0.0.0/1` (две половины default-маршрута), поэтому исходный шлюз по умолчанию не затирается, а IP сервера исключается из туннеля статическим маршрутом через реальный шлюз (защита от петли).
* IPv6-адреса поддерживаются на уровне парсинга SOCKS-адресов целей, но логика исключения сервера из туннеля (`resolve_all_ipv4`) работает только с IPv4 — для `server_host` используйте IPv4 или доменное имя с A-записью.

## 7. Развертывание сервера на Linux (пошагово)

Ниже — полный, воспроизводимый путь «чистый VPS → рабочий сервер». Все команды от root (или через `sudo`).

### Шаг 1. Подготовка системы

```bash
apt-get update && apt-get upgrade -y        # Debian/Ubuntu
timedatectl set-timezone UTC                # по желанию
adduser --disabled-login typroxy            # отдельный пользователь (для файлов)
mkdir -p /opt/typroxy
```

### Шаг 2. Установка бинарника

```bash
# Вариант А: собрать на сервере (см. раздел 4)
# Вариант Б: скопировать готовый кросс-бинарник с машины сборки:
scp dist/typroxy-linux-amd64 root@SERVER:/opt/typroxy/typroxy
chmod 755 /opt/typroxy/typroxy
```

### Шаг 3. Генерация и редактирование конфига

Первый запуск создаст файл и выйдет — это ожидаемое поведение:

```bash
cd /opt/typroxy
./typroxy -c /opt/typroxy/config.toml        # создаст config.toml и завершится
nano /opt/typroxy/config.toml
```

Минимально необходимые правки для сервера:

```toml
mode = "server"

[server]
bind_addr = "0.0.0.0:8888"   # лучше сменить порт (см. раздел 13)
tun_enabled = true
```

### Шаг 4. Пробный запуск в foreground

```bash
cd /opt/typroxy && sudo ./typroxy -c /opt/typroxy/config.toml
```

Ожидаемый вывод:

```
[*] Запуск TLS TyProxy сервера на 0.0.0.0:8888
[+] Создан TUN-интерфейс 'typroxy-srv' (IP: 10.8.0.1)
[+] IPv4 forwarding включен (net.ipv4.ip_forward=1)
[+] Правила NAT (MASQUERADE) и FORWARD в iptables успешно настроены!
```

Остановка — `Ctrl+C` (код корректно обрабатывает SIGINT).

### Шаг 5. Постоянный запуск

Перейдите к разделу 9 (systemd) — ручной запуск в ssh-сессии не переживет разрыв соединения.

### Шаг 6. Проверка снаружи

На сервере: `ss -tlnp | grep 8888` — порт слушается. С клиента (раздел 10/11) — установка TLS-соединения и появление строки `[+] TLS-подключение от <IP клиента>` в логе сервера.

## 8. Автонастройка NAT со стороны сервера (что делает код)

При запуске сервера с `tun_enabled = true` функция `setup_server_nat()` в `src/server.rs` **самостоятельно** выполняет от root:

1. `sysctl -w net.ipv4.ip_forward=1` — включает форвардинг (до перезагрузки!).
2. Проверяет наличие правила и при отсутствии добавляет:
   `iptables -t nat -A POSTROUTING -s 10.8.0.0/24 -j MASQUERADE`
   (обратите внимание: маскарадинг ставится **без привязки к конкретному внешнему интерфейсу**, в отличие от примера с `-o eth0` в README — вариант из кода универсальнее).
3. Добавляет правила FORWARD:
   * `iptables -A FORWARD -i typroxy-srv -j ACCEPT`
   * `iptables -A FORWARD -o typroxy-srv -m state --state RELATED,ESTABLISHED -j ACCEPT`

Этого достаточно для выпуска трафика клиентов в интернет. **Но эти правила живут до перезагрузки или до сброса iptables-цепочек** — их нужно закрепить (раздел 9.2), иначе после ребута сервера туннель поднимется, а интернет из туннеля перестанет работать.

Если в системе вместо legacy-`iptables` используется nft-бэкенд (`iptables-nft`), команды отрабатывают штатно; если фаервол управляется `firewalld`/`ufw` с политиками DROP в цепочке FORWARD — проверьте раздел 13.3.

## 9. Сервер как systemd-сервис + переживание перезагрузок

### 9.1. Юнит сервиса

`/etc/systemd/system/typroxy.service`:

```ini
[Unit]
Description=TyProxy TLS tunnel server
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
WorkingDirectory=/opt/typroxy
ExecStart=/opt/typroxy/typroxy -c /opt/typroxy/config.toml
Restart=on-failure
RestartSec=3
# Серверу нужны root-привилегии для TUN/sysctl/iptables:
User=root
NoNewPrivileges=false

[Install]
WantedBy=multi-user.target
```

Активация:

```bash
systemctl daemon-reload
systemctl enable --now typroxy
systemctl status typroxy
journalctl -u typroxy -f          # живые логи ([+] TLS-подключение от ... и т.д.)
```

> Важно: убедитесь, что `config.toml` уже отредактирован (Шаг 3 раздела 7). Если systemd запустит бинарник без конфига, тот создаст файл, завершится с кодом 0, и при `Restart=always` возникнет быстрый цикл старт-выход до тех пор, пока роль `mode` не станет `"server"`.

### 9.2. Закрепление sysctl и iptables между перезагрузками

Форвардинг:

```bash
echo 'net.ipv4.ip_forward = 1' > /etc/sysctl.d/99-typroxy.conf
sysctl --system
```

Правила iptables (пакет `iptables-persistent` на Debian/Ubuntu или `service iptables save` на RHEL):

```bash
apt-get install -y iptables-persistent     # при установке согласиться сохранить правила
# либо вручную:
iptables-save > /etc/iptables/rules.v4     # каталог создать заранее
```

Альтернатива — скрипт поднятия правил в `ExecStartPost=` юнита. После этого проверьте:

```bash
reboot
# после загрузки:
iptables -t nat -L POSTROUTING -n | grep MASQUERADE
iptables -L FORWARD -n | grep typroxy-srv
ip addr show typroxy-srv
```

## 10. Развертывание клиента: режим SOCKS5

Самый простой и кроссплатформенный способ. Не требует root.

1. Скопируйте бинарник нужной платформы (раздел 5) на машину клиента, например `C:\typroxy\typroxy.exe` или `/usr/local/bin/typroxy`.
2. Первый запуск создаст `config.toml` рядом с текущей директорией; отредактируйте:

```toml
mode = "client"

[client]
server_host     = "SERVER_IP:8888"
routing_mode    = "socks5"
socks_bind_addr = "127.0.0.1:1080"
```

3. Запустите: `./typroxy` (Windows: `.\typroxy.exe`). Ожидаемый вывод:

```
[*] Подключение к TLS TyProxy серверу (SERVER_IP:8888)
[+] Защищенное TLS-соединение установлено!
[*] Выбран режим перехвата трафика: SOCKS5
[+] Модуль SOCKS5 запущен на 127.0.0.1:1080
```

4. Настройте приложения на SOCKS5-прокси `127.0.0.1:1080`:
   * **Браузер:** расширения типа SwitchyOmega / FoxyProxy (SOCKS5). Для Firefox есть нативная настройка Network Settings.
   * **Telegram Desktop:** Settings → Connection type → Custom TCP-over-... / SOCKS5 proxy.
   * **Любые приложения без поддержки прокси:** Proxifier (Windows/macOS) или `proxychains4` (Linux: `proxychains4 curl -v https://example.com`).
5. Поддержка UDP (голосовые звонки, игры) реализована через SOCKS5 UDP ASSOCIATE поверх того же TLS-канала — дополнительных настроек не требуется.

Минус режима: трафик идут только те приложения, которые вы явно настроили; DNS-запросы приложений, работающих мимо прокси, не шифруются.

## 11. Развертывание клиента: режим TUN

Перехват **всего** трафика ОС (Linux-клиент). Требует root.

1. Конфиг клиента:

```toml
mode = "client"

[client]
server_host  = "SERVER_IP:8888"
routing_mode = "tun"
tun_name     = "typroxy-tun"
tun_ip       = "10.8.0.2"
tun_gateway  = "10.8.0.1"
```

2. Запуск: `sudo ./typroxy`. Ожидаемые сообщения модуля TUN:

```
[+] Защита от утечек IPv6 активна (unreachable default ::/0)
[+] DNS-серверы (1.1.1.1, 8.8.8.8) настроены через systemd-resolved для 'typroxy-tun'
```

3. Что код делает автоматически (функция `setup_routes` в `src/modules/tun.rs`):
   * резолвит `server_host` и добавляет **прямые маршруты до IP сервера через реальный шлюз** — трафик до самого сервера не попадает в туннель (защита от петли);
   * создает интерфейс `typroxy-tun` с адресом `10.8.0.2/24`;
   * добавляет маршруты `0.0.0.0/1` и `128.0.0.0/1` через туннель (default-шлюз системы не трогается);
   * ставит `rp_filter=2` на интерфейс;
   * добавляет `ip -6 route unreachable default` — профилактика IPv6-утечек;
   * если в системе есть `systemd-resolved`, переводит DNS на 1.1.1.1/8.8.8.8 через туннель (`resolvectl dns/domain/default-route`); если resolved отсутствует — **DNS остается прежним** (утечка DNS-запросов напрямую; при необходимости пропишите DNS вручную или поставьте resolved/dnscrypt).
   * При остановке процесса (`Ctrl+C`, kill) структура `RouteGuard` в деструкторе **удаляет все добавленные маршруты и настройки** — сеть возвращается в исходное состояние. Поэтому не убивайте процесс сигналом `SIGKILL` (`kill -9`) — после него маршруты останутся висеть, и сеть «не заработает» до ручной чистки:
     `sudo ip route del 0.0.0.0/1 dev typroxy-tun && sudo ip route del 128.0.0.0/1 dev typroxy-tun && sudo ip -6 route del unreachable default metric 1`.

4. Проверка: `curl -s ifconfig.me` должен вернуть **IP сервера**; `ip route show match 0.0.0.0/1` — наличие двух /1-маршрутов.

5. Автозапуск клиента как сервиса (опционально, аналогично разделу 9.1): `WorkingDirectory` должна указывать на папку с `config.toml`, `User=root`, `Restart=on-failure`. Учитывайте отсутствие автопереподключения: при обрыве TLS-соединения процесс завершится, systemd поднимет его заново.

## 12. Клиент под Windows и macOS

* **Windows:** доступен только SOCKS5-режим. Поместите `typroxy-windows-amd64.exe` и `config.toml` в одну папку (например `C:\typroxy\`), запустите двойным кликом или из cmd: `typroxy-windows-amd64.exe`. Первый запуск создаст конфиг — запустите второй раз после редактирования. Для перехвата «всего системного трафика» используйте Proxifier с правилом на `127.0.0.1:1080`. Разрешите программу в Windows Defender Firewall при первом запросе (исходящие соединения обычно не блокируются).
* **macOS:** SOCKS5-режим: `./typroxy-darwin-arm64` (или amd64). При первом запуске Gatekeeper может заблокировать неподписанный бинарник — снимите блокировку в System Settings → Privacy & Security («Все равно открыть») либо `xattr -d com.apple.quarantine ./typroxy-darwin-arm64`. Настройку системного SOCKS-прокси: `networksetup -setsocksfirewallproxy Wi-Fi 127.0.0.1 1080`, отключение — `networksetup -setsocksfirewallproxystate Wi-Fi off`.
* **FreeBSD:** только SOCKS5-режим, аналогично Linux.

## 13. Сетевые требования, firewall и провайдер

### 13.1. На стороне сервера

Открыть входящий TCP-порт в фаерволе провайдера/ОС:

```bash
# ufw
ufw allow 8888/tcp
# firewalld
firewall-cmd --permanent --add-port=8888/tcp && firewall-cmd --reload
# чистый nftables/iptables
iptables -A INPUT -p tcp --dport 8888 -j ACCEPT
```

Если используется cloud security groups (AWS/GCP/Yandex/OVH) — откройте порт и там.

### 13.2. Совмещение с существующим HTTPS-сервером

Так как трафик выглядит как TLS, порт `443` мог бы отдавать и обычный сайт, и туннель — но **реализация TyProxy не различает протоколы**: на порту сервера принимается только TLS с ALPN `typroxy`, обычные браузерные handshake будут отбиты (`TLS Handshake error` в логе). Варианты:

* держать TyProxy на отдельном порту (рекомендуется);
* либо на отдельном IP того же VPS;
* полноценный front-proxy (nginx stream / tls-alpn routing) поверх TyProxy кодом не тестировался — самый предсказуемый путь: отдельный порт.

### 13.3. Политика FORWARD

Многие дистрибутивы с `docker`/`firewalld` ставят policy `DROP` на цепочку FORWARD. Код добавляет точечные ACCEPT-правила, но если после включения docker правила переставились — проверьте `iptables -L FORWARD -n` и при необходимости поднимите политику или добавьте свои правила (раздел 9.2).

### 13.4. На стороне клиента (домашняя сеть)

Исходящий TCP на порт сервера не должен блокироваться провайдером/корпоративным фаерволом. Если порт 8888 подозрителен цензору — смените порт сервера на `443` (если он свободен) или иной «популярный» (8443, 2053, 2083...). ALPN задан жестко (`typroxy`) и через конфиг не меняется.

## 14. Безопасность: что нужно понимать хостеру

Честный список свойств реализации (по коду):

1. **Отсутствие аутентификации вообще.** Любой, кто узнает `IP:порт`, сможет подключить свой клиент и пользоваться вашим сервером как прокси/VPN: резолвить домены, ходить в интернет с вашего IP, нагружать канал. Никаких токенов/парольных фраз нет, `wallet_path` — фикция. Меры снижения риска:
   * нестандартный порт + ограничение доступа по IP в фаерволе (`iptables -A INPUT -p tcp --dport 8888 -s ВАШ_IP -j ACCEPT; ... -j DROP`) — если у вас статический адрес;
   * мониторинг логов (`journalctl -u typroxy` печатает `[+] TLS-подключение от <IP>` — чужие подключения видны сразу);
   * лимиты канала/трафика на уровне VPS.
2. **Нет проверки сертификата сервера** (см. раздел 1, п. 4) — возможна MITM-деанонимизация. Шифрование «от попутного DPI» работает, криптографической гарантии личности сервера нет.
3. **Сертификат ephemeral** — новый ключ генерируется на каждый запуск; ротация происходит бесплатно, отзыв не нужен (и невозможен).
4. **Логи.** Сервер пишет в stdout только служебные события (подключения, ошибки) — никаких журналов посещений сайтов не ведется. Тем не менее провайдер VPS видит ваш трафик целиком на физическом уровне.
5. **Юридический аспект.** Хостинг обходного средства связи регулируется законодательством страны дата-центра и вашей страны; размещая сервер, вы отвечаете за весь трафик, идущий с вашего IP. Проект позиционируется авторами для личного использования (предупреждение в начале README).
6. **Отказоустойчивость.** Нет автопереподключения клиента, нет балансировки, один TCP-канал на клиента; при потери сети клиентом все сессии теряются. Для продакшена обязательны `Restart=` в systemd (разделы 9, 11.5).

## 15. Диагностика и типовые проблемы

| Симптом | Причина | Решение |
|---|---|---|
| Программа запустилась и сразу завершилась без ошибок | Первый запуск: создан `config.toml` | Отредактировать конфиг, запустить снова |
| `[-] Ошибка инициализации TUN (требуется root)` на сервере | Запуск без root / нет `/dev/net/tun` | `sudo`; в контейнере — проброс `/dev/net/tun` + capability `NET_ADMIN` |
| TLS-соединение не устанавливается | Порт закрыт/заблокирован, неверный `server_host`, конфликт ALPN | `nc -vz SERVER_IP PORT`, проверить фаерволы (раздел 13) |
| `TLS Handshake error` в логе сервера | К порту обращаются обычные браузеры/сканеры или другой протокол | Нормально, игнорировать; при массовости — сменить порт |
| SOCKS5 подключается, сайты не открываются | Сервер не может резолвить/достичь целей | На сервере: `resolvectl status`/`/etc/resolv.conf`, исходящий трафик |
| TUN поднимается, ping 10.8.0.1 есть, интернета нет | Не работает форвардинг/NAT на сервере | `sysctl net.ipv4.ip_forward`, `iptables -t nat -L -n`; правила после reboot (раздел 9.2) |
| После `kill -9` клиента интернет «пропал» | Маршруты не удалены (деструктор не вызван) | Удалить вручную команды `ip route del 0.0.0.0/1 ...` (раздел 11.3) |
| Трафик идет, но DNS «светится» наружу (TUN) | Нет systemd-resolved на клиенте | Настроить resolved или вручную направить DNS в туннель |
| Клиент теряет связь при обрыве и не восстанавливается | Автопереподключения нет | Systemd-юнит с `Restart=on-failure` для клиента |
| Двойной NAT/хостинг за роутером (сервер дома) | Внешний порт не проброшен | Port-forward TCP на роутере или DynDNS + DMZ |
| Сборка `make darwin/bsd` падает | Нет `zig`/`cargo-zigbuild` | Раздел 5 |

Полезные команды наблюдения:

```bash
journalctl -u typroxy -f                 # логи сервера
ss -tlnp | grep typroxy                  # слушается ли порт
ip addr show typroxy-srv                 # состояние TUN на сервере
watch -n1 'iptables -t nat -L POSTROUTING -n | tail'   # NAT-счетчики (растут ли пакеты)
tcpdump -i typroxy-srv -nn               # видны ли IP-пакеты от клиента 10.8.0.2
```

## 16. Обновление и удаление

### Обновление сервера

```bash
systemctl stop typroxy
cp /opt/typroxy/typroxy /opt/typroxy/typroxy.bak        # резервная копия
# новая сборка/копия бинарника:
scp dist/typroxy-linux-amd64 root@SERVER:/opt/typroxy/typroxy
chmod 755 /opt/typroxy/typroxy
systemctl start typroxy && systemctl status typroxy
```

Конфиг форматно совместим между сборками 0.1.x; при изменении схемы — сравните с шаблонным файлом, который программа сгенерирует при отсутствии `config.toml`.

### Полное удаление сервера

```bash
systemctl disable --now typroxy
rm /etc/systemd/system/typroxy.service && systemctl daemon-reload
rm -rf /opt/typroxy
# снять NAT/форвардинг, если они больше не нужны:
iptables -t nat -D POSTROUTING -s 10.8.0.0/24 -j MASQUERADE
iptables -D FORWARD -i typroxy-srv -j ACCEPT
iptables -D FORWARD -o typroxy-srv -m state --state RELATED,ESTABLISHED -j ACCEPT
ip link del typroxy-srv
rm /etc/sysctl.d/99-typroxy.conf
iptables-save > /etc/iptables/rules.v4   # перезаписать сохраненные правила
```

Удаление клиента: остановить процесс **штатно** (Ctrl+C / SIGTERM — сработает очистка маршрутов), удалить бинарник и `config.toml`.
